# 3.2.0 后台统一识别与手机轻量同步

本次由独立分支 `feature/backend-order-authority` 发布为 3.2.0 正式私人版。手机和后台应成套升级；不承诺旧客户端与新后台的全部组合。保留订单历史、人工决定及尚未确认的离线操作。NAS 由用户自行更新。

## 升级顺序

先拉取后台镜像 `ghcr.io/zsdd2/kdyzm:3.2.0`（或 `latest`），沿用原数据卷、配置和加密密钥启动，确认后台版本为 3.2.0。随后从后台提供的 App 更新入口下载并覆盖安装 3.2.0 / 30200。后台内置同版 APK、更新清单及校验文件，手机可直接从后台下载，不需要访问 GitHub。

保留现有 App，不能先卸载或清除数据。后台与手机都在首次处理旧数据前自动备份；备份失败时停止相关修改。源码备份已经保存，生产数据备份仍需等各端首次运行新版本时生成。

## 分工

后台负责淘宝、拼多多、京东采集、物流状态与时间证据、站点和柜位、派送员号码、识别异常重试与既有 AI 工作流。手机消费统一的 `platformView`；缺失或冲突字段明确待核对，不再用手机另一套物流规则重新推断平台结果。

手机负责读取短信、提取取件信息、与后台规范包裹匹配、显示结果、人工校验和离线操作。相同取件码或唯一候选仍不能绕过运单、站点、时间和数量约束。人工站点修正与未获后台回执的确认操作优先保留。

| 操作 | 行为 |
| --- | --- |
| 打开首页 | 先显示本地快照，后台同步不会阻塞已有卡片操作 |
| 扫描短信 | 扫描并本地匹配，不等待平台采集 |
| 普通后台同步 | 读取已整理的轻量快照；整账号上次成功采集超过 30 分钟才请求补采 |
| 手动刷新平台或订单 | 提交独立采集任务，状态与本地扫描分开 |
| 展开物流详情 | 单独请求该运单轨迹，不重新采集平台 |
| 确认收到 | 本地先持久记录，后台按操作 ID 幂等接收并精确回执 |

后台仍按每平台默认 15 分钟、平台之间错开 5 分钟调度。保留原 AI 开关、自动应用设置和每日预算；本次没有增加模型调用。

## 同步协议

设备使用原设备 Bearer 身份读取 `GET /v1/snapshot?view=compact`。首次返回所有获授权实体及 `dataVersion`，物流事件放到详情接口。以后带 `dataVersion`；实体和授权范围相同时返回 `metadataOnly:true`，只传账号、任务和规则摘要，不传订单数组。ETag 继续处理整个响应都未改变的情况。

`dataVersion` 包含身份范围及业务实体，不包含纯采集检查时刻。业务证据或规则变化会改变运单 `evidenceKey`，使详情缓存失效。权限变化强制完整同步。客户端区分实体版本与元数据版本，拒绝旧响应；元数据更新不能清空实体。

`GET /v1/shipments/:id/logistics` 逐运单校验权限并解析历史别名。响应包含规范 ID、订单 ID、`evidenceKey` 和轨迹。客户端只接收与当前绑定、包裹及证据版本一致的结果。详情失败只影响当前展开区域；局部缓存不能覆盖新状态、确认结果或人工站点修正。

同类同步请求合并；任务摘要已在快照中时不再逐任务查询。遗漏任务每轮最多查询三个，其余保留至下轮。短信扫描、物流详情和确认收到各有自己的等待状态。

这版使用实体版本复用，尚未采用逐字段增量补丁。新订单变化时重新发送轻量实体集合，避免稀疏字段误清空原值。

响应按 UTF-8 字节限制为 4 MB，后台为完整快照预留余量，主体控制在 3.8 MB。超限明确失败，手机保留本地记录和同步游标；不会截掉必要身份或状态冒充同步成功。输入请求的原上限不变。单用户当前采用有界完整实体集合，未来真实数据超限时再增加分页。

## 业务边界

- 京东仓库准备、打印和等待揽收保持待发货，只有明确揽收才确定发货时间。手机列表和桌面小组件消费同一后台等待标志。
- 京东、顺丰明确送到门口时使用该事件时间作为到达时间，用户确认时间作为签收时间。
- 门店卡位留在站点名称中；具体柜号作为子位置，原始站点文本继续保留以核对冲突。
- 已到站但平台没有有效时间时保持未知，不能用采集时刻填补。
- 打开详情不会改变已关闭提醒；新业务证据才允许提醒重新出现。

## 备份与恢复

发布前已在开发电脑保存 3.1.52 源码基线及本次改版前逐文件 SHA-256 清单，均留在本地，不上传个人数据。

后台首次用 3.2.0 打开已有数据库时，先用 SQLite `VACUUM INTO` 在数据库目录的 `upgrade-backups` 下产生独立备份，再进行迁移。同目录的 `service-config.json` 存在时也私密复制。备份失败则停止启动，不继续迁移；新空库不产生旧数据备份。

手机首次处理非空旧状态前，将完整原始 JSON 写入 App 私有目录 `files/upgrade-backups/assistant-state-before-3.2.0.json`。临时文件写盘后原子改名，已有有效备份不覆盖；错误目标或存储失败阻止本次修改。备份包括短信、历史订单、规则、设置和离线队列。浏览器本地预览另保存在 `pickcode.private.backup.pre-3.2.0`。

恢复后台前必须停止服务，另存当前数据库及 WAL/SHM，再以备份替换数据库，不复用新库的 WAL/SHM。恢复配套配置、旧版服务及原环境加密密钥；备份不产生替代密钥。手机恢复应在停止 App 后，将私有 JSON 恢复为 SQLite `assistant_state` 的原 payload，并清除可重新生成的显示缓存，再安装配套版本。普通手机无法直接读私有目录时需调试授权或设备备份能力；请勿先卸载 App，因为卸载会删除私有备份。

本次不远程修改生产业务数据。NAS 更新及更新后的真实手机验收由用户执行。
